Research: GreenGrid spec baseline

type: planned-featurestatus: complete 2026-09-27commit 9f310e4main Riadh Gharbi

GreenGrid Java Edition is specified as a 10-day proof of concept that watches about 200 solar sites: it registers and onboards them, polls three inverter vendors, keeps every invalid reading for audit, detects outages and underproduction, and emails operators — built as five Spring Boot microservices around Kafka and MongoDB, secured by Keycloak and shipped by GitOps.

The repository today holds the Chapter 1 foundation only: a green multi-module build, five empty service skeletons, an empty shared events library and a one-command local infrastructure stack. Everything the business will notice is still ahead. Five contradictions in the spec that would have changed the design were settled on 2026-09-27 (see Open questions → Clarifications); two Compose defects should be fixed before Chapter 2.

Key findings

  • The build foundation works: BR-001 is implemented; all other rules are ahead, as expected at this stage.
  • Local infrastructure is partial (BR-002): the Kafka controller variable is misspelled and likely stops the broker (INC-008), and the replica set lacks the priority Chapter 2 relies on (INC-003).
  • Every service calls itself site-registry (INC-001) and the gateway module is a copy of a normal service (INC-002).
  • Settled with you: per-interval gap detection (INC-012), detection for Active sites only (INC-027), resume polling on reactivation (INC-014), an IANA time zone per site (INC-028), manual resolve by operators (INC-013).
  • Several anomaly and messaging edge cases are unspecified: clearing rules (INC-029), verification count reset (INC-030), outbox poison entries (INC-031), reading write order (INC-017).

Concepts worth knowing

Ideas this area relies on that may be new to you — explained first, so the rest reads easily.

Bounded context

Big domains use the same word for different things (a "site" to onboarding is not a "site" to monitoring). A bounded context draws a line inside which every term has exactly one meaning. GreenGrid splits its services along these lines, so each service owns its own model and data.

flowchart LR
  R[Registry<br/>Site = lifecycle] -- site events --> I[Ingestion<br/>Site = source to poll]
  R -- site events --> M[Monitoring<br/>Site = health profile]
Here: One context per service (§3.1). The spec's ubiquitous language (glossary below) is meant to appear verbatim in class, event and topic names.

Hexagonal architecture

Put the business rules in the middle with no framework code, define interfaces (ports) for what they need, and plug technology in at the edges (adapters: REST controllers, Kafka listeners, Mongo repositories). The core can then be tested without any infrastructure.

flowchart LR
  In[adapter/in<br/>REST, Kafka listener] --> App[application<br/>use cases + ports]
  App --> Dom[domain<br/>plain Java]
  Out[adapter/out<br/>Mongo, Kafka, vendor] -. implements ports .-> App
Here: Every service has empty domain, application, adapter.in and config packages; adapter.out is not created yet. ArchUnit should enforce the arrows (BR-004).

Anti-corruption layer

When you integrate with an outside system whose model you don't control, translate at the border so its quirks never leak into your domain. Each vendor gets its own adapter that turns its payload into the domain's Meter Reading.

flowchart LR
  SE[SolarEdge JSON] --> A1[SolarEdge adapter]
  FR[Fronius JSON] --> A2[Fronius adapter]
  EN[Enphase JSON] --> A3[Enphase adapter]
  A1 & A2 & A3 --> MR[Meter Reading<br/>UTC, kWh]
Here: Ingestion, one adapter per brand behind a common port (BR-018); vendor DTOs must not leave their adapter package.

Transactional outbox

Saving data and publishing an event are two systems; if the service crashes between them, one happens without the other. The outbox writes the event into a table in the same database transaction as the change, and a separate relay publishes it afterwards. The event can then never be lost — only delivered more than once.

sequenceDiagram
  participant S as Service
  participant DB as MongoDB
  participant R as Relay
  participant K as Kafka
  S->>DB: tx: save Site + outbox entry
  R->>DB: find unsent entries
  R->>K: publish, wait for ack
  R->>DB: mark sent
Here: greengrid-events will hold the envelope, writer and relay (BR-003); it needs the MongoDB replica set because Mongo transactions require one. The library is empty today (INC-007).

Idempotent consumer

At-least-once delivery means a consumer can see the same event twice. An idempotent consumer remembers the ids it has processed (in the same transaction as its state change) and silently skips repeats.

flowchart LR
  E[event id 42] --> C{seen 42?}
  C -- no --> P[apply + remember 42]
  C -- yes --> X[skip]
Here: processed_events in each consuming service (BR-012); readings use a different trick because time-series writes cannot join a transaction (INC-017).

MongoDB replica set

Three copies of the same data: one primary takes writes, two secondaries follow and can take over. Beyond resilience, a replica set is what enables multi-document transactions and change streams.

flowchart LR
  App[service] -->|writes| P[(mongo1 primary)]
  P --> S1[(mongo2)]
  P --> S2[(mongo3)]
Here: Compose runs rs0 with three members (TC-010). Host-run services connect directly to mongo1, so mongo1 must be the preferred primary — the missing priority (INC-003).

KRaft

Kafka used to need a separate ZooKeeper cluster to store its metadata. KRaft is Kafka's built-in consensus mode: a broker can also act as controller, so a single container is a complete Kafka.

Here: One combined broker/controller node, reachable as localhost:9092 from your machine and kafka:19092 inside Compose (TC-011).

Time-series collection

A MongoDB collection type optimized for measurements over time: documents are bucketed internally by a meta field (here the site) and time, which makes range queries and storage much cheaper than a plain collection.

Here: Monitoring's readings collection with minute granularity (BR-023).

Dead-letter topic

When a message keeps failing (bad data, unknown site), retrying forever blocks everything behind it. After a few retries the error handler moves it to a side topic for inspection, and processing continues.

flowchart LR
  T[topic] --> L[listener]
  L -- fails 3x --> D[topic.DLT]
  L -- ok --> OK[state updated]
Here: Registry's listener for source events: 3 retries at 1 s, then the DLT (BR-012).

Lease / ShedLock

When two replicas run the same scheduled job, it runs twice. A lease is a lock with an expiry stored in the database: whoever takes it runs the job, and if that replica dies the lock simply expires.

Here: The outbox relay, the gap detector and the poller (BR-003, BR-017, BR-025); required so old and new pods can run side by side during canaries.

EARS requirements

Easy Approach to Requirements Syntax: a handful of sentence patterns (WHEN … THE SYSTEM SHALL …, IF … THEN …, WHILE …) that make requirements precise and directly testable.

Here: Every business rule in this document (BR-001…BR-039) is written in EARS so the plan phase can turn each into acceptance tests.

Canary release

Instead of switching everyone to a new version at once, send a small share of traffic to it, watch error metrics, and promote step by step — or roll back automatically when metrics degrade.

flowchart LR
  V[new version] --> C20[20%] --> A{errors > 5%?}
  A -- no --> C50[50%] --> C100[100%]
  A -- yes --> RB[rollback]
Here: Argo Rollouts with a Prometheus analysis (BR-008); not started.

GitOps / app-of-apps

The desired cluster state lives in a Git repository; a controller (Argo CD) continuously makes the cluster match it. Deploying means committing. App-of-apps is one root application that points to all the others.

Here: A separate greengrid-gitops repository watched by Argo CD (BR-006, BR-007); not created yet.

How it flows

The target scenarios end to end, and the only flow that runs today.

Onboarding a site (target)

  1. A CS agent registers a site with customer, region and installation (BR-010) — status Registered.
  2. The agent adds vendor connection details (BR-011) — ConnectionPending; Ingestion learns about the new source from an event, never by calling the registry (BR-016).
  3. Ingestion polls; the first success moves the site to Verifying, three successes to Active (BR-012).
  4. Failures while verifying send it back; the pipeline view lists sites stuck longer than 48 h (BR-014).
  5. The agent may suspend and later reactivate the site (BR-013); Ingestion resumes normal polling on reactivation (BR-016, decided in Q-003).

From reading to alert (target)

  1. Ingestion polls a site on its brand interval and normalizes the vendor payload (BR-017, BR-018).
  2. Invalid readings are kept with a reason and announced (BR-019); valid ones are announced (BR-020).
  3. Monitoring stores each reading once and updates site health (BR-023, BR-024).
  4. Gaps, underproduction, rejection bursts or unreachable sources open an anomaly (BR-025…BR-027, BR-031).
  5. Each new anomaly raises exactly one alert, which becomes one email (BR-029, BR-032).
